# Divergences — `strutture.loads.vento` (tool `vento-pressione`)

Source: `Carico vento da NTC - DM2018.xls`, sheet `Vento` (scalars) + `Tabelle` (zone/categoria
lookups, pressure-profile fill-down). Spec: `docs/specs/vento.md` §A. Bugs per spec §7 and
`docs/architecture.md` §6.

| `Vento!H7` | Wind zone `VLOOKUP(H5, Comuni!D:J, 3, FALSE)` is keyed on `H5` (the resolved **provincia** name) against column D, which is **Comune**, not Provincia — a copy-paste bug. It only returns a result at all when some comune happens to be named exactly like the province (`_zona_da_provincia_legacy` in `comune_zona.py`); otherwise it fails the way Excel's `#N/A` would. Empirically the zone is uniform within every province in `src/strutture/data/comuni.csv` (checked: 0/106 provinces have a mixed `zona_vento`), so when a same-named comune *does* exist the bug happens to return a numerically correct value anyway. | `zona = comune.zona_vento`, read directly off the resolved comune row — always correct, never fails for a province whose name isn't also a comune name (e.g. "Monza e Brianza": no comune is named that, only "Monza" is; see `test_zona_da_comune_legacy_bug_fallisce_senza_capoluogo_omonimo` / `test_zona_da_comune_fixed_funziona_dove_il_legacy_fallisce` in `tests/loads/vento/test_comune_zona.py`). | §3.3.1 / spec §7 | None on the golden case (comune="Milano" — a province whose name coincides with a comune, so both modes return `zona=1`). | `Vento!H15` (`vR(TR)`, return-period correction) | `vR(TR) = vref·sqrt(fattore_gumbel(TR)/fattore_gumbel(50))` — renormalises the Gumbel factor against its own value at `TR=50` (bakes `ln(-ln(0.98))`), applied **unconditionally** regardless of mode. The exposed `aR` (Vento!H14, output field `a_r`) is the *un-renormalised* `cr(TR) = 0.75·sqrt(1−0.2·ln(−ln(1−1/TR)))`, so `a_r·vref ≠ vr` in the sheet at every `TR ≠ 50` — a real inconsistency an engineer reproducing the chain by hand would flag as an error, and was previously not documented here at all. | `legacy_compat=False` (default): `vr = vref·a_r` with no renormalisation (NTC2018 eq. 3.3.2/3.3.3) — `a_r·vref == vr` exactly, by construction. `legacy_compat=True`: keeps the sheet's `/cr(50)` renormalisation for `vr` (`velocita_riferimento(..., legacy_compat=True)`) while `a_r` (`coefficiente_periodo_ritorno`) stays the un-renormalised `cr(TR)`, so the sheet's own inconsistency (`a_r·vref ≠ vr`) is still reproduced intentionally in that mode. | §3.3.2 eq. 3.3.3 | None on the golden case's own `TR=50` (the sheet's normalisation baseline: `fattore_gumbel(50)/fattore_gumbel(50)=1` exactly, so `vr=vref=25` m/s identically in both modes — this is exactly why the bug was invisible at the golden `TR`). ## Da verificare

- `Tabelle!O` column ("cev") stores `sqrt(ce(z))` (a velocity multiplier: `vp = O·vR`), not `ce(z)`
  itself — spec §7 originally flagged this as a possible ce-vs-ce² inconsistency between `H37` and
  the profile table, but spec §8 already retracts that: `P[n] = 0.5·ρ·(O·vR)² = qb·ce(z)`, the same
  `ce(z)` formula used for the scalar `H37`/`H45`. Confirmed independently here: `esposizione.py`'s
  single `coefficiente_esposizione()` is reused for both the scalar `ce_h` and every profile row, and
  the oracle test (`tests/loads/vento/test_oracle.py`) checks `riga.ce == pytest.approx(row["O"] ** 2)`
  across 8 zones/categories with no failures. Not treated as a divergence needing a `legacy_compat`
  branch — both modes use the same `ce(z)` definition, matching the sheet's actual (non-buggy) formula.
- The raw `Vento`/`Tabelle` region label for at least one province ("Abruzzo ") carries a stray
  trailing space in the source workbook's `Comuni` sheet that the curated
  `strutture.shared.comuni` build normalises away (see `tests/loads/vento/test_oracle.py`, which
  `.strip()`s the oracle's `regione`/`provincia` cells before comparing). This is a whitespace/data
  hygiene artifact in the legacy `Comuni` sheet's `Regione` column, not a calculation divergence — no
  `legacy_compat` branch was added for it since neither mode should reproduce a typo in a display
  label sourced from the *other* agent's `comuni` module.
